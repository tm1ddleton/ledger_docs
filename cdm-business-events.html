FINOS Common Domain Model · v6.0.0 · Event Model

Anatomy of a BusinessEvent,
by worked decomposition

In the CDM a lifecycle event has no declared type. A BusinessEvent is composed from a fixed set of primitive operators applied to a before trade state, producing one or more after states — and its identity is inferred from that composition. Below: the frame, then four events decomposed into primitives, intent, and inferred qualifier — then, in 06–08, how the lifecycling engine builds on this: the registry and grain that key it, the projection and provenance that reconcile it, and the CDM profile that documents every divergence.

00

The frame

A Workflow wraps the event; the BusinessEvent carries an eventDate, an optional intent, and an inferred eventQualifier; each Instruction binds one composite PrimitiveInstruction to a before TradeState. The product stays immutable — only events that change the economics spawn a new product/trade instance.

the fork: what goes in the NonTransferableProduct

Note-as-security (settlement lens). economicTerms = a single SettlementPayout buying the note for cash; underlier = the RC note as a TransferableProduct (a Security carrying the coupon-and-put payoff). Faithful to how it trades — but coupon & redemption become asset-servicing, which the CDM deliberately does not model.

Note-as-contractual-product (economic-terms lens). economicTerms directly compose the contingent coupon payout + the embedded short-put / settle-in-shares OptionPayout + principal. The trade is the structured product — the lens the later panels assume, since coupon and knockout act on these very terms.

Either way the trade is wrapped in a NonTransferableProduct (1..1) even though the note itself may be transferable: the bilateral terms still have to be agreed. The transferable / non-transferable boundary, in one object.

Why execution is the odd one out. It is the only primitive with no before-state — it creates rather than transitions. So a fresh trade gets no lifecycle eventQualifier the way coupon/knockout/corporate-action do; the inference runs on the product (qualification functions tag the economic terms as a structured note with an embedded option), and contractFormation is what the event itself records.

02

Contingent coupon

A coupon payment on a reverse convertible with a memory feature.

RC · memory coupon Equity-linked coupon, observed then paid

A note pays a periodic coupon only if the underlying equity fixes at or above the coupon barrier on the observation date; missed coupons accumulate and are released on the next in-barrier date (the memory). The coupon amount is fixed — the equity fixing only gates it. So the equity level is recorded as an Observation, the barrier/memory logic lives in the economic terms, and the result is a single transfer. No reset: nothing in the cashflow consumes the observed value. The product is never touched.

the test: consumed vs tested

reset earns its place only when the observed value is consumed as a value in the cashflow formula — a floating leg fixing SOFR, an equity-swap performance leg locking the period price. The payout literally cannot compute the transfer until that variable price slot is filled.

Here the equity level is tested as a condition (above/below the barrier) and the coupon is fixed, so there is no variable price attribute for Reset.resetValue (a mandatory Price) to bind to — a reset would be a dangling record. The conditionality belongs in the economic terms; the observation is just recorded.

Same equity, opposite role. An equity swap on this very name would use reset — there the observed price drives the return and is consumed by the performance leg. The reverse convertible observes the same price but only to open or shut a gate, which is why reset adds nothing and the event reduces to Observation → transfer.

the ambiguity you have to resolve

1 · Which sub-attribute? A listed quantityChange must be qualified as targeting quantity.value (contracts, Convention A) or quantity.multiplier (deliverable, Convention B). The primitive name alone is underspecified — both dimensions live inside the same quantity object.

State, settlement & aggregation

Every event so far has written to a TradeState. Two questions follow: what does the state on a single trade look like, and how do many trades roll up into a position? Both are computed, never declared — the position is the accumulated effect of replaying events.

Rune — the two state dimensions and the cross-field rule

type State:
  closedState ClosedState (0..1)        // the reason: Terminated, Matured, Exercised…
  positionState PositionStatusEnum (0..1)  // the risk-lifecycle marker

  condition ClosedStateExists:
    if positionState = PositionStatusEnum -> Closed
    then closedState exists

enum PositionStatusEnum:
  Executed   // risk transferred — the point of execution
  Formed     // contract formed (contractual product)
  Settled    // settled after execution, e.g. securities
  Cancelled  // cancellation following an execution
  Closed     // closed via a termination event

Two attributes, not one. positionState is the coarse "where in life" marker; closedState carries why it ended. The knockout panel set closedState = Terminated; the invariant above is what forces that reason to be present whenever positionState reaches Closed.

two position shapes — don't conflate them

Position / PortfolioState is the portfolio-aggregation construct: a grouping by product or asset, computed by replay. The NonTransferable condition requires its products be NonTransferableProducts — consistent with trades wrapping even transferable underliers.

CounterpartyPosition is a separate, richer type: positionIdentifier (incl. UTI), openDateTime, party/partyRole including the clearing organisation, and tradeReference to every constituent TradeState. This is the CCP-aware shape — the one that maps to the cleared-member exposure picture.

Materialise, but reconcile. Replaying from genesis on every query is expensive, so PortfolioState is built as a chain of snapshots you extend from the latest — the same caching discipline as a knock-in latch or a product-version cache. The lineage (globalKey hashes into the prior state and the events) is what lets you prove a snapshot is faithful and rebuild it if you don't trust it.

Rune — one offset machine, two anchors

type RelativeDateOffset extends Offset:   // Offset extends Period
  periodMultiplier int           // 2   (from Period)
  period PeriodEnum               // D   (from Period)

//          anchor = trade date, +2 Business

two different offsets — don't merge them

Settlement cycle (equity) is on SettlementDate.adjustableOrRelativeDate, anchored to trade date. It answers "when does the trade settle."

Payment lag (coupon) is PaymentDates.paymentDaysOffset (an Offset), anchored to the calculation-period end via payRelativeTo. It answers "how long after the coupon is determined does the cash move." Positive multiplier = delayed payment; negative = early.

Same Offset primitive underneath; different home and different anchor. Both resolve to the one Transfer.settlementDate.

Determination is not payment. The coupon panel's event fires on the determination date — but the transfer it emits carries a settlementDate that is the period end plus the payment lag. So a business event's eventDate and the cash-movement date legitimately differ. For your wrapper, the offset is an input you resolve against calendars at the boundary; the canonical trade keeps the parametric rule so a calendar change re-resolves correctly.

06

From anatomy to engine

The anatomy is descriptive: every event is primitives over a before state. The engine adds one claim — every lifecycle event is versionₙ₊₁ = f(trigger, versionₙ): a stateless function, polymorphic in its trigger, that fans out atomically across every position on the prior version and projects to canonical CDM events at the boundary. Two structural choices make that tractable.

engine · fOne function, four triggers

An announced corporate action, a self-determined observation breach, a terms amendment, an index transition — different triggers, one signature. The function reads the current version and returns the next version plus the moves; it stores nothing of its own.

layer · registryProducts pre-exist; trades reference them

A contract month is listed before anyone trades it; an OTC term sheet is registered before the position books. The product is a pre-existing entity keyed by (productId, version) at the payout layer — and trades reference the product, never the reverse. That inversion is what lets many trades share one set of terms by construction.

listed vs OTCpayoff identical · only booking topology differs

Listed-vs-OTC is not a structural fork at the payoff layer. The same option payoff is the same template whether it clears at a CCP or faces a bilateral name; the venue is a field on the entry. The two-leg exchange booking model is a property of the settlement layer, not the product — so one lifecycle engine serves both. A barrier capability is template metadata; the runtime barrier_knocked latch (the cache of §05) stays on unit state.

engine · grainLifecycling grain is a consequence of fungibility

A product is lifecycled at one of two grains, declared on its registry entry. The choice is not free — it follows from whether one product version is shared across many trades.

grain = position
fungible / listed
cash equity · futures · cleared IRS. Events service the position; per-trade CDM events are projected at the boundary.
grain = trade
bespoke OTC
OTC option · bilateral note. The product version is unique per trade, so position == trade and no projection runs.

The two cases meet at the boundary. A trade-grained product is the degenerate position-grained one where every position holds exactly one trade — because for bespoke terms the product version component of the position key is unique per trade. One model; the flag just records which side you are on.

07

Two grains, projected · provenance, not shape

Position-level events (dividend, variation margin, corporate action) are computed once against the position, then down-allocated losslessly to per-trade CDM events for reconciliation and counterparty interop. And two events with the same economic effect carry the same shape however they arose — only provenance distinguishes them.

project · down-allocationOne CCP figure → many internal moves

The CCP delivers a single net variation-margin amount against the exchange-facing book. The ledger explodes it to one allocation per internal wallet — and the parts sum back exactly to the whole. 08

The profile — resolving CDM's ambiguities

Section 04 ended on an unresolved listed-option quantityChange; section 05 left positionState caching as a discipline. Wherever the CDM is thin or admits more than one valid representation, the engine publishes the choice. A documented mapping is a profile; a model CDM cannot express is a fork.

profile · four resolutionsWhere CDM offered a choice, here is ours

quantity.value vs multiplier

Position size N = number of contracts in quantity.value; point value carried once as the product multiplier (Convention A of §04). Splits adjust value; the deliverable stays a terms property.

reset vs observation

The observation (fixing, barrier level, settlement price) is the canonical source; the reset onto the move is a derived view. Disagree ⟹ observation wins, reset recomputes.

asset vs payout · listed option

Modelled at the payout layer (OptionPayout), same as OTC; the listing is metadata. One option engine; the CCP appears only as the counterparty wallet.

STM vs CTM · margin

Cleared & title-transfer VM = settled-to-market (the cost-basis reset of §05's futures); security-interest CSA = collateralised. Initial margin is collateral, out of scope.

corporate action that changes the ladder

A merger that re-dates the coupon schedule writes a new product version whose terms regenerate the QRL ladder. The engine reconciles the new ladder against events already actioned on the prior version: survivors keep their marker, dropped events are cancelled, new ones schedule as Expected. No special case — it is just f(trigger, versionₙ).

version bump, but no re-bucketing

On a fungible underlying the new version applies in place, atomically across every subscribed position (inv. 12). The unit id is stable; positions are not re-bucketed — re-bucketing would strand per-position state (cost basis, open Pending(date), exercise sub-buckets) with no migration rule. Same end state, none of the plumbing.

Profile, not fork

Every resolution above keeps the engine interoperable: a CDM-native counterparty receives standard events because the divergences are documented mappings, not silent reinterpretations. The bespoke extensions that remain — DailySettlementEvent, the Expected state, the compound unit state — are flagged forks, reviewed against each CDM release. The full register lives in docs/profile.md.
